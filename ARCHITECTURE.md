# Großer Adler V1 — Minimal Architecture

## 1. Purpose
Großer Adler is an independent second look on running work. It reads primary evidence, records evidence-bound findings, and places the current advisory view beside an explicitly known Grabowski worktree. It does not execute or steer the work.
Its independence is observational and authority-path based, not cognitive: a same-turn Adler observation is never an independent decision review.

## 2. Authority Boundary
Adler owns observation, verification, advisory findings, the immutable finding store, and computed inbox files under its own state root. Grabowski owns work identity, decisions, claims, leases, tasks, product mutations, Git index/commit/push, pull-request mutation, merge, deployment, service/process control, credentials, effect policy, and the worktree-local `.adler` pointer metadata. Severity is not authority.

Non-Git laboratory evidence is a separate observation surface: Adler may list directories and read bounded UTF-8 text only below the fixed `/home/alex/labs` root. Resolution must fail closed on path or symlink escape, directory scans and text windows are bounded, and text is passed through the same secret redaction as other observer output. Git tools remain confined to `/home/alex/repos`; lab observation adds neither shell, generic filesystem, root, nor write authority.

## 3. Finding Contract
`finding_contract="adler-finding-v1"` identifies the contract family and retains the `submit_finding_v1` tool name. Historical records with `schema_version=1` remain readable and projectable; new submissions always persist `schema_version=2`. The reader accepts exactly these two integer versions for this family. Schema 1 must not contain `target_lane_id`; its only lane binding is an exact `lane:<32 lowercase hex>` subject. Schema 2 permits optional `target_lane_id` (exactly 32 lowercase hexadecimal characters) as the canonical binding, independent of the human-readable `subject`. If absent, the exact `lane:<id>` subject remains a compatibility fallback; if both bindings are supplied they must agree or the request is rejected before append. Neither free text nor `evidence_refs` supplies a delivery binding. Unbound findings remain durable without lane projection. Rechecks across supported schema versions must retain the original subject and resolved lane target. Delivery uses the same binding for immediate projection and full-history rebuilds and retains the existing server-side lane, pointer and checkpoint checks. Inbox views contain each `finding_id` at most once, without rewriting or coalescing distinct historical findings.

Rollback is fail-closed: the base reader at `5a9e20b6bed90fd75e6453b2488a35b6198a3461` accepts only integer schema 1 for `adler-finding-v1` in `_validate_v1_finding_payload`. It quarantines schema 2 and reports `source_complete=false` instead of silently accepting records whose explicit target it cannot interpret. The current reader likewise quarantines unknown versions and schema 1 records containing `target_lane_id`; no automatic downgrade or history rewrite occurs. This version rule is separate from the historical legacy contract schemas below. An isolated probe using the unchanged `server.py` from that Git object confirmed validator rejection of newly submitted schema 2 records with an explicit target, a subject fallback, or no binding. With those records and a historical schema 1 fixture in temporary state, the base listing and lane projection reported incomplete sources while retaining the historical finding; the current reader reported a complete source. Reproduce this check by importing the base Git object as a temporary module against temporary state. This Git-object probe stays outside unit tests; unit tests exercise the current reader directly without copying the base implementation.

New-capable clients use `submit_finding_v1` and persist `adler-finding-v1`: `schema_version`, `finding_id`, `finding_sha256`, `kind`, `severity`, `confidence`, `subject`, optional `target_lane_id` (schema 2 only), `checkpoint`, `binding_strength`, `summary`, `evidence_refs`, optional `recommendation` and `affected_effects`, plus `observed_at`. Kinds are `observation`, `risk`, `contradiction`, `missing_evidence`, or `advice`. The digest covers the complete stored core, including `schema_version` and any `target_lane_id`, but is an integrity check, not an authenticity signature. Record views expose `schema_version`. Changes are appended as new recheck records; historical records are never rewritten. A recheck always references the original root finding, never another recheck. `submit_finding` is a narrow compatibility ingress for already-cached historical ChatGPT connector catalogs: it accepts only the old base shape, persists the historical subject/checkpoint shape instead of inventing V1 `confidence`, `binding_strength`, or checkpoint authority, and may project that record into the existing inbox only when a canonical `grabowski_lane` subject is accompanied by an explicit non-empty checkpoint supplied by the request that still matches the exact current lane checkpoint. Free-form historical lane subjects and blank/omitted checkpoints remain durable but are not delivery bindings. Such inbox entries remain visibly `legacy=true` / `binding_strength=legacy-unbound`; they are never silently upgraded to V1. Other historical legacy records remain readable but do not define V1 delivery semantics; malformed or ambiguous V1-like records are not downgraded to legacy.

## 4. Worktree-Sidecar Contract
Grabowski remains authoritative for `lane_id`, repository, worktree, branch, and purpose. `get_work_target` may observe an exact registered Grabowski lane target anywhere under the allowed repository root; observation alone does not establish sidecar-delivery eligibility. Delivery is deliberately narrower: the lane worktree must also be under Adler's configured `WORKTREE_ROOT`, and Grabowski must have created the local `.adler/` metadata plus an exact `.adler/inbox.json` symlink to Adler state at `<state>/worktree-inboxes/<lane_id>.json`. A target that is observable but outside that delivery root fails delivery closed. Adler validates the pointer but writes only the external target under its own state root. The resolved inbox remains a computed current view for the worktree HEAD, reconstructible from the central finding store, and never canonical history. Git exclusion and pointer creation belong to Grabowski; Adler has no worktree, Git-metadata, or Git-index write authority. No finding-to-task/lane resolver exists.

## 5. Explicit Non-Goals
V1 has no Adler work-state database, current_work overlay, supervision lifecycle, delivery queue, acknowledgements, task conversion, admission engine, generic file writer, shell, coding-agent start, Bureau mutation, product write, Git-index mutation, commit, push, PR mutation, merge, deploy, service control, process signal, credential mutation, or generic probe sandbox.

## 6. Failure Semantics
The immutable finding is persisted before inbox delivery is attempted. Delivery requires the exact Grabowski-owned worktree pointer and never creates or repairs that pointer. Delivery failure never rolls back history and never means “no findings”. Invalid JSON, a malformed/ambiguous V1 record, a digest mismatch, or any other unreadable canonical finding is logically quarantined from the valid projection and remains visible through store-health evidence; the canonical file is never rewritten, moved, repaired, or discarded. A lane inbox may still be published with `source_complete=false`, an explicit quarantine count, and bounded quarantine details, so one bad historical record does not globally suppress valid current evidence. The inbox is a bounded, reconstructible current-view cache rather than canonical history: when the current set exceeds the byte budget, severity-ordered findings are compacted with explicit `projection_complete=false` and omission counts instead of raising solely because the finding set is large. Same-checkpoint root findings may advance a process-local index of already validated canonical finding records without rescanning every historical payload. The published sidecar is output only and is never used as membership truth. A SHA-256 watermark over the canonical finding filenames must prove that exactly one new finding file was appended since the indexed snapshot; otherwise the index is discarded and an authoritative full-history scan is performed. Full scans classify the exact same filename snapshot that they hash, including dot-prefixed JSON names, and cannot claim source_complete=true unless every watermarked name is either validly loaded or explicitly quarantined. Incremental advance re-snapshots membership after validating the new canonical record, and the finding-store shared lock is held through atomic inbox publication so cooperating appends cannot slip between the accepted watermark and the published view. Rechecks likewise force a full scan. The incremental path deliberately does not re-observe every historical payload byte, so it publishes fail-closed with `source_complete=false` and `source_rescan_required=true`. The in-memory index disappears on process restart and is then rebuilt from canonical history. Syntactically corrupt JSON at the exact Adler-owned inbox state path is repairable from canonical history, while a valid inbox naming a foreign writer identity remains non-overwritable. An absent, invalid, failed, or checkpoint-stale inbox is unknown/stale, not evidence of absence. Normal local work remains possible when Adler is unavailable. Any later protected-effect policy belongs to Grabowski and consumes facts only; Adler never returns ALLOW, DENY, or BLOCK.
